# 要件定義書:AIを活用した英語リズム学習支援ツール

**文書バージョン**: 1.0
**作成日**: 2026年8月
**対象授業**: Clear Speech(後期)
**目的**: 学会発表(ICT・AI活用教育)のための教材開発 兼 研究データ収集

---

## 1. プロジェクト概要

### 1.1 何を作るか
ブラウザ上で動作する、AIを活用した英語プロソディ(リズム・アクセント)学習支援ツール。
学生が英文の「内容語は強く長く、機能語は弱く短く」という英語特有の強勢拍リズム(stress-timed rhythm)を、
視覚的に理解し、実際に発音し、AIによるフィードバックを受けられる教材とする。

### 1.2 位置づけ(学会発表用)
表向きのテーマは「発音」ではなく、**「生成AIを活用したリアルタイム視覚フィードバック教材の設計と開発」**とする。
発音はそのコンテンツの一部という位置づけであり、ICT・AI活用教育の文脈で発表することを前提に設計する。

### 1.3 背景・課題認識
- 日本語はモーラ拍(mora-timed)言語、英語は強勢拍(stress-timed)言語であり、リズムの取り方が根本的に異なる。
- 英語には「内容語(名詞・動詞・形容詞・副詞など)は強く読む/機能語(代名詞・前置詞・助動詞・冠詞など)は弱く読む」という原則があるが、日本人学習者はこれを知らずに全ての単語を均等な強さ・長さで発音しがちである。
- 機能語には強形(strong form)と弱形(weak form)があり、意味的な強調がない限り弱形が標準的に使われる(例: `can` は多くの文脈で /kən/ であり、/kæn/ ではない)。この知識がないため、リスニング・ディクテーションで機能語が全く聞き取れない、あるいは不自然に強く発音してしまうという問題が生じている。
- 英単語の発音は前後の単語との連結(リンキング、同化、脱落など)によって変化するが、辞書に載っている単独の発音としか結び付けられていない学習者が多い。

### 1.4 ゴール
1. 学生が英文中の内容語・機能語・強形/弱形を視覚的に区別して理解できる。
2. 学生が自分の発話を録音し、期待されるリズムパターンと比較できる。
3. AIによる音声認識・音響解析を用いて、内容語が明瞭に発音されているか、機能語が適切に弱形で発音されているかについてフィードバックを与える。
4. 授業(Clear Speech)での利用を通じて、学習効果を測定できるデータを匿名化して収集し、学会発表に活用する。

---

## 2. 対象ユーザー・利用規模

- **対象学生**: Clear Speech受講者、1クラス20〜40人程度。
- **利用環境**: 大学のPC教室、または学生個人のノートPC/スマートフォン(要件次第でスマホ対応は Phase 2 以降でも可)。
- **利用ブラウザ**: Google Chrome を第一対象とする(Web Speech API 依存のため)。
- **指導者**: 教員(本人)が全体の進捗・提出状況を確認できることが望ましい。

## 3. スコープ

### 3.1 MVP(Minimum Viable Product)— まずここまで動くものを作る

| # | 機能 | 内容 |
|---|------|------|
| 1 | 例文プロソディ表示 | 内容語/機能語のサイズ・強調差、強形/弱形の対比表示(既存プロトタイプの内容を土台とする) |
| 2 | 例文セット管理 | 教員があらかじめ用意した例文(10〜20文程度)をアプリ側で管理できる(コード内のデータ配列で可) |
| 3 | モデル音声再生 | ブラウザTTSによる参考音声(既存プロトタイプ相当。精度の限界は許容) |
| 4 | 録音機能 | 学生がマイクで発話を録音できる |
| 5 | 音量カーブの可視化 | 録音した音声の振幅(RMS)を時系列で表示し、内容語の位置に山ができているかを視覚的に確認できる |
| 6 | 音声認識による簡易フィードバック | Web Speech APIでの認識結果と目標文を比較し、内容語の脱落/機能語の弱形化を区別してコメントする |
| 7 | 学生識別(簡易) | 学籍番号または匿名ID(教員が事前配布する連番など)を入力させ、データに紐付ける |
| 8 | データ送信・匿名保存 | 学生ID(匿名化ID)・例文ID・音量カーブデータ・認識結果・タイムスタンプを、サーバーに送信し保存する |

### 3.2 Phase 2(MVP後の拡張)

| # | 機能 | 内容 |
|---|------|------|
| 9 | 教員用ダッシュボード | クラス全体の提出状況、例文ごとの正答率・傾向を一覧表示 |
| 10 | 発話ごとの録音音声そのものの保存 | (要:同意取得・倫理審査。3.4節参照) |
| 11 | 例文の追加・編集用UI | コードを直接いじらずに、教員が例文を追加できる管理画面 |
| 12 | ピッチ(音の高さ)解析 | 強勢のもう一つの要素であるピッチの変化も可視化する |
| 13 | 学生向け進捗表示 | 自分がこれまで取り組んだ例文数、傾向のフィードバック履歴 |
| 14 | スマートフォン対応 | レスポンシブ対応、タッチ操作最適化 |

### 3.3 Phase 3(研究・発表向け高度化、任意)
- フォーストアライメント(単語ごとの発話開始・終了時刻の精密推定)による、より正確な単語別ストレス測定
- 複数回の発話比較による習熟度の時系列グラフ
- 統計解析用のデータエクスポート機能(CSV等)

### 3.4 データ収集・倫理面の重要な前提条件(要検討・要対応)
録音データ(音声そのもの)を保存・分析する場合、人を対象とする研究となるため、以下が前提条件となる。開発着手前に確認すること。

- **倫理審査**: 所属機関の研究倫理委員会(またはそれに準ずる審査プロセス)の承認が必要になる可能性が高い。
- **インフォームドコンセント**: 学生に対して、データの利用目的(授業内フィードバック/研究発表)・匿名化の方法・保存期間・拒否した場合の代替措置を明示し、同意を得る仕組みが必要。
- **匿名化の設計**: 学籍番号や氏名を直接保存せず、教員のみが対応表を管理する形の匿名IDを採用することを推奨。
- **MVP段階では「音量カーブなどの数値データ」のみを保存対象とし、音声データそのものの保存はPhase 2以降、倫理審査が整い次第とする**、という段階的な設計を推奨する。

## 4. 機能要件(詳細)

### 4.1 プロソディ表示
- 例文データは「単語, 品詞タイプ(content/function), 強形IPA, 弱形IPA(あれば), 補足ノート」を持つ構造とする(既存プロトタイプのデータ構造を踏襲・拡張)。
- 内容語は大きな文字・大きなビートマーカーで、機能語は小さな文字・小さなビートマーカーで表示する。
- 弱形が存在する機能語は、強形に取り消し線、弱形を強調表示する。

### 4.2 録音・解析
- ブラウザのマイク入力(`getUserMedia`)を用いて録音する。
- 録音中、音声の振幅(RMS)を一定間隔でサンプリングし、時系列データとして保持する。
- 録音終了後、振幅データを平滑化した上でグラフ表示する。
- 可能であれば、音声認識(Web Speech API)を並行して実行し、認識結果テキストを取得する。

### 4.3 フィードバック
- 目標文の単語リストと、音声認識結果を単語単位で比較する。
- 内容語が認識されなかった場合:「発音が不明瞭な可能性」としてコメントする。
- 機能語が認識されなかった場合:「弱形として自然な可能性がある」旨をコメントし、内容語の脱落とは区別して表示する。
- 音量カーブ上で、内容語の位置に想定される振幅の山ができているかを視覚的に確認できるようにする。

### 4.4 データ送受信
- MVP: 匿名ID・例文ID・振幅データ(配列)・認識結果テキスト・タイムスタンプをサーバーAPIに送信する。
- サーバー: シンプルなデータベース(例: SQLite等の軽量DBから開始し、規模に応じて拡張)にレコードとして保存する。
- 教員が後でエクスポート(CSV等)できるようにする(Phase 2または3)。

## 5. 非機能要件

- **対応ブラウザ**: Google Chrome(最新版)を必須要件とする。Web Speech APIの制約上、Safari/Firefoxでは音声認識が動作しない可能性がある旨、利用者に明示する。
- **通信環境**: 学内Wi-Fi等、標準的な教室のネットワーク環境で問題なく動作すること。
- **同時アクセス**: 1クラス最大40人程度が同時にアクセス・録音してもサーバーが問題なく処理できること。
- **プライバシー**: 通信は暗号化(HTTPS)すること。ローカルサーバー(`http://localhost`)での開発段階から、本番環境では独自ドメイン+HTTPSでのホスティングを想定する。
- **可用性**: 授業時間内(90分程度)、安定して稼働すること。

## 6. 技術構成(案)

| レイヤー | 技術(案) | 備考 |
|---|---|---|
| フロントエンド | HTML / CSS / JavaScript(既存プロトタイプをベースに拡張) | フレームワーク導入は必須ではないが、機能拡張が進む場合はReact等も検討 |
| 音声認識 | Web Speech API(ブラウザ標準) | Chrome依存。将来的により高精度なAPI(例:サーバーサイドでのASR)への切り替えも Phase 3 で検討可 |
| モデル音声 | ブラウザ標準TTS(`speechSynthesis`) | 精度に限界があるため、Phase 2でより自然な音声(録音済みネイティブ音声等)への差し替えも検討 |
| バックエンド | 軽量サーバー(例: Node.js + Express、または Python + FastAPI) | Claude Codeでの開発時に選定 |
| データベース | SQLite(小規模から開始)、必要に応じPostgreSQL等へ移行 | 匿名化ID・数値データ中心のため大規模DBは初期不要 |
| ホスティング | 大学内サーバー、または学外クラウド(要:所属機関のデータ取り扱いポリシー確認) | 学生データを扱うため、所属機関のガイドラインに従うこと |

## 8. 成功基準(評価指標の案)

- 学生が例文ごとに内容語/機能語の区別、強形/弱形の違いを説明できるようになったか(事前・事後の簡易テスト等で測定)。
- ディクテーションにおける機能語(弱形)の誤答パターンに変化が見られるか。
- 音量カーブ上で、内容語のピークが授業前後で明瞭になったか(定量データとして収集)。
- 学生の主観的な有用性評価(アンケート)。

## 10. 参考:現行プロトタイプとの対応関係

現行プロトタイプ(`prosody_prototype.html`)は、上記 4.1(プロソディ表示)、4.2(録音・振幅解析)、4.3(音声認識フィードバックの一部)を
単一HTMLファイル・ブラウザ内完結の形ですでに実装済みである。
MVP開発では、このロジックを土台として、4.4(データ送受信)とサーバー側の実装を追加する形で進めることができる。
